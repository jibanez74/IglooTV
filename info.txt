Yes, your question is clear. You can compile AAC and DCA into the extension, package them permanently with the app, and decide at runtime whether a playback session uses FFmpeg.

One terminology distinction:

* “Decode with FFmpeg” means AAC/DTS becomes multichannel PCM.
* “Passthrough” means the encoded AAC/DTS stream bypasses FFmpeg and goes to HDMI unchanged.

## Global user setting

A simple setting could be:

```text
FFmpeg audio decoding
- Enabled
- Disabled
```

When creating the player:

```kotlin
val extensionMode =
    if (settings.ffmpegAudioDecodingEnabled) {
        DefaultRenderersFactory.EXTENSION_RENDERER_MODE_PREFER
    } else {
        DefaultRenderersFactory.EXTENSION_RENDERER_MODE_OFF
    }

val renderersFactory =
    DefaultRenderersFactory(context)
        .setExtensionRendererMode(extensionMode)
        .setEnableDecoderFallback(true)

val player = ExoPlayer.Builder(context, renderersFactory).build()
```

The FFmpeg native libraries remain installed in the application either way. `OFF` simply prevents Media3 from creating and selecting the FFmpeg renderer.

This setting must be applied while constructing the player. You cannot change the renderer mode on an existing `ExoPlayer` instance.

## Per-codec settings

You could also expose:

```text
AAC
- Use device decoder/passthrough
- Decode to PCM with FFmpeg

DTS and DTS-HD
- Use device passthrough
- Decode to PCM with FFmpeg
```

Because Igloo knows the selected audio track before starting playback, it can decide how to construct that playback session:

```kotlin
fun shouldUseFfmpeg(
    audioFormat: Format,
    settings: AudioDecoderSettings,
): Boolean =
    when (audioFormat.sampleMimeType) {
        MimeTypes.AUDIO_AAC ->
            settings.decodeAacWithFfmpeg

        MimeTypes.AUDIO_DTS,
        MimeTypes.AUDIO_DTS_EXPRESS,
        MimeTypes.AUDIO_DTS_HD ->
            settings.decodeDtsWithFfmpeg

        else -> false
    }
```

Then:

```kotlin
fun createRenderersFactory(
    context: Context,
    audioFormat: Format,
    settings: AudioDecoderSettings,
): DefaultRenderersFactory {
    val mode =
        if (shouldUseFfmpeg(audioFormat, settings)) {
            DefaultRenderersFactory.EXTENSION_RENDERER_MODE_PREFER
        } else {
            DefaultRenderersFactory.EXTENSION_RENDERER_MODE_OFF
        }

    return DefaultRenderersFactory(context)
        .setExtensionRendererMode(mode)
        .setEnableDecoderFallback(true)
}
```

The effective behavior would be:

| Setting             | Selected track | Result                       |
| ------------------- | -------------- | ---------------------------- |
| AAC FFmpeg enabled  | AAC            | FFmpeg → PCM                 |
| AAC FFmpeg disabled | AAC            | Android renderer             |
| DTS FFmpeg enabled  | DTS-HD         | FFmpeg → PCM                 |
| DTS FFmpeg disabled | DTS-HD         | Android renderer/passthrough |
| Any setting         | TrueHD         | Android renderer/passthrough |

TrueHD remains unaffected because the FFmpeg build does not contain the `truehd` decoder.

## Important limitation

`EXTENSION_RENDERER_MODE_PREFER` applies to every decoder compiled into the extension. Media3 does not provide a built-in runtime call such as:

```kotlin
preferFfmpegFor(MimeTypes.AUDIO_AAC)
```

Therefore, the session-based approach works when Igloo knows which audio track will initially play. But consider this case:

1. The user enables FFmpeg for AAC.
2. The user disables it for DTS-HD.
3. A movie contains both AAC and DTS-HD tracks.
4. The player was constructed with `PREFER` because AAC was initially selected.
5. The user switches to DTS-HD during playback.

Because `dca` is also compiled and FFmpeg remains preferred, the existing player may decode DTS-HD through FFmpeg despite the user’s DTS setting.

You have two practical solutions.

### Rebuild the player when the audio policy changes

When the user selects an audio track requiring a different renderer policy:

1. Save the current playback position.
2. Save `playWhenReady`.
3. Release the player.
4. Construct it with the new renderer mode.
5. Restore the media, position, subtitle selection, and playback state.

This is reasonably simple but may cause a brief interruption.

### Add a custom codec-aware renderer policy

For seamless switching, you would need a custom integration that allows the FFmpeg renderer to claim support conditionally:

```kotlin
AAC && settings.decodeAacWithFfmpeg
DTS_HD && settings.decodeDtsWithFfmpeg
```

The official `FfmpegAudioRenderer` is `final`, so it cannot simply be subclassed. You would need to maintain a small customized copy of the renderer integration, modify the Media3 extension, or implement more advanced renderer selection.

I would not start there.

## Recommended Igloo design

I recommend two levels:

```text
Audio decoding

Automatic — Recommended
Prefer passthrough
Prefer local PCM decoding
```

Then an advanced section:

```text
Codec overrides

Multichannel AAC
- Automatic
- Decode to PCM
- Use device handling

DTS / DTS-HD
- Automatic
- Decode to PCM
- Use device passthrough
```

The automatic policy for your current goals could be:

```text
AAC with more than 2 channels → FFmpeg PCM
DTS-HD                     → FFmpeg PCM
AAC stereo                 → Android decoder
DTS core                    → Device handling
AC3/E-AC3/TrueHD            → Device passthrough
```

Initially, I would implement the session-based approach and apply codec changes on the next playback. It is considerably simpler than modifying Media3 and still gives the user meaningful control. If seamless switching between differently handled audio tracks later becomes important, you can introduce a codec-aware renderer policy then.
